# P&G 수주·배송 포털 (한익스프레스 TPL2팀)

P&G 오더 엑셀 업로드 → 검증 → 가온 자동 수주등록 → 배차 → 직송은 기사 모바일(TMS) 추적, 거점경유는 간선 출고 시 완료 간주 → P&G 화주 조회.

## 화면

P&G 블루(#003DA5) 기준 색, 네이비 사이드바 + 상단바 레이아웃, Pretendard 글꼴(CDN, 없으면 Malgun Gothic).
모든 화면은 `templates/base.html`(사이드바 레이아웃) 또는 `templates/bare.html`(로그인 · 기사 접속) 위에 올라가고, 스타일은 `static/style.css` 한 파일입니다.
기사 링크 화면은 사이드바 없는 모바일 레이아웃입니다.

## 배포(Lightsail)

서버 설치·갱신 절차는 deploy/README.md 참고. 시연 서버: https://pg.3-39-129-208.sslip.io (설치 후).

## 실행

- `실행.bat` 더블클릭 (또는 `py app.py`) → http://127.0.0.1:5070
- 필요 패키지: flask, openpyxl, requests, segno(QR) (배치가 없으면 자동 설치)
- 데이터: `data/portal.db`(SQLite), `data/uploads/`, `data/pod/`(인수증 사진). `data/`만 백업하면 됨.
- 초기 관리자 계정: 아이디 `1111` / 비밀번호 `1111` (임시, 처음 생성 시엔 admin / hanex1234) → 로그인 후 **관리 > 사용자**에서 비밀번호를 바꾸세요.
- 외부(P&G·기사) 접속용 배포 시: 환경변수 `PGPORTAL_HOST=0.0.0.0`, HTTPS 리버스 프록시(nginx/caddy) 뒤에 두고, 관리 > 설정의 `public_url`에 외부 주소를 넣어야 기사 링크가 외부 주소로 생성됨. 가온 계정은 관리자만.

## 처음 쓰는 순서

1. **마스터 > 거점센터 / 차량 / 기사** 등록 (엑셀 양식 내려받아 일괄 등록 가능)
2. **마스터 > 납품처**: P&G 코드 ↔ 가온 점포코드, 거점 지정. 직송/거점은 규칙으로 판정하되 '강제 유형'을 두면 그 납품처는 고정
3. **마스터 > 상품**: P&G 코드 ↔ 가온 상품코드, 입수 EA/BOX · BOX/PLT · EA/PLT → 오더 BOX·PLT 자동 계산. P&G 상품마스터 엑셀을 그대로 올려도 헤더(상품코드/SKU/Material, 박스입수, BOX/PLT …)를 자동 인식
   - **직송/RDC 기준은 날짜마다 담당자가 정함**: 분리 · 양식 화면 상단의 '그날 직송 기준 PLT'를 입력하면 그 납품일의 배차 전 오더가 다시 판정되고, 납품처별로 직송/RDC를 직접 지정(규칙 무시)하거나 규칙으로 되돌릴 수 있음. 업로드 검증 화면에서도 기준을 입력해 확정 가능. 설정의 값은 날짜별 기준이 없을 때의 기본값
   - **직송/거점 판정 규칙(관리 > 설정)**: 기본 `route_mode=plt` — 업로드 확정 시 **같은 납품일 + 같은 납품처**의 오더 PLT를 기존 등록분까지 합쳐 `direct_plt_threshold`(기본 3) 이상이면 직송, 미만이면 거점경유. 배차 전 오더는 추가 업로드가 오면 다시 판정됨. 거점경유 판정인데 거점이 없으면 설정에 따라 직송 또는 오류 보류. 오더 수량 단위가 BOX/CS 등이면 박스 수로 환산. '배차 전 오더 다시 판정' 버튼으로 기준 변경 후 일괄 재판정
4. **관리 > 설정**: 화주코드, 기본 출고센터, 엑셀 컬럼 매핑(샘플 확정 후 헤더명 고정)
5. **오더 업로드** → 검증 미리보기 → 확정 → 오더·운송 구간 생성
6. **가온 등록**: 가온 연결 후 대기 오더 선택 → 등록 (※ 통신 재현은 HAR 분석 후 연결 예정)
7. **배차(직송만)**: 납품일별 직송 운송 건에 **차량번호·기사 이름·휴대폰**을 입력해 배정(없는 차량·기사는 자동 등록, 용차 대응) 또는 자동배차. 기사 링크가 발급되어 '복사' 버튼으로 카톡·문자에 붙여넣거나 차량별 배정표의 QR로 전달. '재발급'은 이전 링크·기기 묶음을 해제. 배차 해제 시 남은 배차가 없으면 링크 무효. **RDC(거점) 오더는 분리·양식 단계에서 끝나며(상태 'RDC 분리') 운송 건을 만들지 않는다**
8. 직송 건은 기사 `/m`에서 **센터 도착 → 센터 출발 → 점포 도착 → 배송 완료(인수증)** 순으로 버튼을 누름. 버튼마다 폰 GPS를 같이 보내고,
   - 센터 도착·센터 출발 때 납품처 좌표까지 **예상 도착시각**을 계산(OSRM 경로 API, 실패 시 직선거리×도로계수/평균속도 추정)
   - 점포 도착 때 납품처 좌표와의 거리로 **실제 도착 검증**(설정 반경, 기본 500m)
   - 현황(대시보드)·오더 상세·P&G 조회에서 현재 단계·시각·예상도착이 보임. GPS 로그는 ship_logs 테이블
   - ※ 브라우저 GPS는 **HTTPS(또는 localhost)에서만** 동작 → 기사용 배포는 반드시 HTTPS. 납품처 마스터에 위도·경도가 있어야 예상도착이 계산됨
   - **지오코딩**: 관리 > 설정에 카카오 REST API 키를 넣으면 ① 마스터 > 납품처/거점의 **좌표 채우기** 버튼(좌표 없는 행만 / 전체 다시), ② 엑셀 일괄 등록 직후, ③ 오더 업로드 확정 직후(해당 납품처)에 주소→좌표를 자동으로 채움.
     원문 → 괄호·층/호 제거 → 뒤 토큰 절단 → 장소 키워드 검색 순으로 시도하고 결과는 geocode_cache에 저장. 실패 건은 화면에 이름이 표시되므로 주소를 고치거나 위도·경도를 직접 입력

## 오더 상태 흐름

직송: 접수(received) → 가온등록(gaon) → 배차(dispatched) → 센터도착(center_arrived) → 센터출발(shipped) → 점포도착(store_arrived) → 배송완료(delivered) / RDC: 접수 → RDC 분리(rdc, 종료)
- 오류(error): 납품처·상품 미등록 등. 마스터 보완 후 다시 업로드하거나 상태 수동 변경
- 운송 구간(shipments): 직송만 1구간(센터→납품처). RDC는 운송 구간 없음
- 오더 상태는 운송 구간 상태로부터 다시 계산됨 (`core/service.py: recompute_status`)
